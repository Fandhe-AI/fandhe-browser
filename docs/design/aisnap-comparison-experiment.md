- **対応ビヘイビア**: AISNAP-9（Must・検討中）。関連: AISNAP-8（簡約方式単体 70% 以上）・AISNAP-15（対生 DOM シリアライズ比。分母の定義）
- **対応タスク**: TASK-22（前提 TASK-21）。Conditional Go 条件 2(c) を引き継ぐ
- **マイルストーン**: MS-2
- **参考**: PoC-4（簡約方式単体 88.0% = 22/25。生 DOM 直渡し方式との比較は未実施）

- **状態**: 草案。「未決定（オーナー判断待ち）」と書いた箇所は #123 のオーナー判断に無い案で、実験着手前に確定する

## 目的

`AISNAP-9` は、同一タスクセットを簡約方式（方式 B）と生 DOM 直渡し方式で実行したとき、簡約方式の操作成功率が生 DOM 方式に対し **-5 ポイント以内**（同等以上）であることを求める。
PoC-4 は簡約方式単体の絶対値評価（`AISNAP-8`）しか行っておらず、本実験で直接比較する。

## 生 DOM 入力の作り方

AISNAP-15 の分母（生 DOM シリアライズ）と同一の定義を使う。実装は `benches/token_reduction/raw_dom.rs` の `serialize_raw_dom` で、PoC-4 `reduce.mjs` の `rawDomSerialize` の移植である。

1. 対象 fixture（`benches/fixtures/<page>.html`）を core のパーサーで DOM に構築する。
2. `serialize_raw_dom` で、除去対象要素を部分木ごと取り除いた `body` の outerHTML 相当文字列を得る。
3. 得られた文字列をそのままエージェントへ渡す（成形・要約・追加の整形はしない）。

**要判断（定義の差異）**: オーナー判断は「`<script>` と `<style>` を除いた」とするが、AISNAP-15 の分母の実装（`serialize_raw_dom`）は `script`・`style`・`noscript`・`svg`・`link`・`meta` の 6 種を部分木ごと除去し、`body`（無ければルート要素）を対象にする。AISNAP-15 の記述も「`<script>`/`<style>` 等を除去」であり「等」を含む。
本書は「AISNAP-15 の分母と揃える」という判断の趣旨を優先し、`serialize_raw_dom` の 6 種除去を既定とする案で書く。判断文どおりの 2 種のみ除去にする場合は分母と一致しなくなるため、どちらにするかを確定する（未決定（オーナー判断待ち））。

補足:

- `serialize_raw_dom` は測定専用の簡易シリアライザで、jsdom の `outerHTML` との完全一致は保証しない（`raw_dom.rs` の注記）。本実験でも同じ出力を使う。
- 生 DOM 入力は実験用に `<page>.html` から一括生成して固定し、全回答者へ同一内容を渡す。生成物をコミットするか実験時の一時ファイルとするかは未決定（オーナー判断待ち。案: 一時ファイル。再生成は決定的なため）。

## 回答形式

簡約方式の回答は ref を返す形式で、`score.rs` が採点する（`harness/agent_eval/README.md`「採点」）。生 DOM には ref 番号が無いため、そのままでは回答形式が揃わない。

案（未決定）: 生 DOM 方式の回答は、要素を CSS セレクタと文書順 index の組 `{selector, index}` で答えさせる。golden のロケータ形式（`fandhe_browser_core::query::query_selector_all_str` の結果の文書順 `index` 番目）と同じため、採点時にロケータ同士で照合できる。`value`（extract）と `steps`（form）の構造は簡約方式と同じにする。

この回答形式の差は、方式間で「要素を指す難しさ」が異なる点を実験に持ち込む。限界節に記録し、採点基準（後述）をどちらかに有利にしないことを確認する。

## ブラインド手順

PoC-4 の追加検証（`03-poc/ai-interface-token-reduction/README.md`「追加検証: AI操作成功率の実測」）と同じく、サブエージェントによる手動実行とする。API 経由の LLM 自動実行は採らない（後述）。

### 割付表

25 タスク × 2 方式を、各タスクで「先に見る方式」を入れ替えて割り付ける。

1. タスクを id 昇順に並べ、種別（click・extract・form・nav）ごとに「簡約 → 生 DOM」と「生 DOM → 簡約」を交互に割り当てる。奇数個の種別（click 7）は余りを次の種別の先頭から続ける。これで全体の先頭方式が 13 件対 12 件以内に収まり、種別内の偏りも最大 1 件になる。
2. 割付表は golden を見ずに作る。表は固定し、回答者へは渡さない。
3. 割付表の列: タスク id・種別・ページ・先に提示する方式。

要判断: 「提示順の入れ替え」は同一タスクを同一回答者が両方式で解く前提だと学習効果（先に見た方式で答えを知る）が残る。
本書は、1 タスクにつき方式ごとに独立したサブエージェント（会話を共有しない）へ渡す案とする。その場合の提示順は 1 回答者内の入力順ではなく、実行の順序と回答者割当の入れ替えとして扱う。解釈はオーナー判断（「方式の提示順をタスクごとに入れ替える」）の意図に照らして確定する（未決定（オーナー判断待ち））。

### サブエージェントへの指示テンプレート（骨子）

```text
あなたは Web ページ上の操作を判断するエージェントです。
入力: 1 つのページの表現（<方式に応じて簡約表現 または 生 DOM>）と、タスク文 1 件。
出力: 指定の JSON 形式の回答のみ。

規則:
- 与えられた表現だけを根拠に答える。それ以外の資料・ファイル・ページを参照しない。
- 表現から特定できない場合は推測せず、回答不能（null）と答える。
- 回答形式: <方式別の回答形式。簡約 = ref、生 DOM = {selector, index}>
```

- 渡すもの: タスク文（`tasks.json` の `prompt`）と、そのタスクのページの表現 1 つのみ。
- 渡さないもの: golden 全般、他タスクの回答、他方式の表現、fixture 原本、リポジトリの他ファイル、実験の意図（比較であること・判定式）。
- 回答者は 1 回の実行で 1 タスク 1 方式のみ解く。生 DOM の回答者にはリポジトリ参照を許さない（fixture 原本から `golden` が推測できてしまうため）。
- 回答は JSON として保存し、回答不能は `null` のままにする。ref の「でっち上げ」を防ぐため、PoC-4 と同じく「特定できなければ回答不能」と明示する。

## 採点と判定

### 採点基準

golden との照合は、簡約方式は `score.rs` の既存基準（TASK-21.3）をそのまま使う。

| golden | 合格条件（簡約方式。`score.rs` と同じ） | 生 DOM 方式（案。未決定） |
| ------ | -------------------------------------- | ------------------------ |
| `ref`（click・nav） | 回答 ref が解決済み ref のいずれかに一致 | 回答ロケータが golden の `any_of` のいずれかのロケータと同一要素を指す |
| `value`（extract） | 空白を正規化した完全一致（大文字小文字は区別） | 同じ |
| `steps`（form） | 手順数・各手順の action・ref・value が順序どおりに一致 | 同じ。ref はロケータで比較 |

- **部分点は付けない**（案。未決定）。タスク単位で合格 1 / 不合格 0 とする。部分点を許すと簡約方式の ref 構造への依存度が結果に混入するうえ、25 件では解釈が難しくなるため。
- 不合格の分類は `score.rs` と揃える（`unanswered`・`invalid_shape`・`mismatch`・`golden_unresolved`）。
- `golden-refs.json` で解決不能な golden（extract-01 など）は簡約方式側で `golden_unresolved` になりうる。生 DOM 方式は ref を使わないため比較の公平性に影響しうる。該当タスクの扱い（除外するか含めるか）は未決定（オーナー判断待ち。案: 含めたうえで除外時の差を併記する）。

**要実装確認**: `score.rs` は ref 形式の回答のみを扱う。生 DOM のロケータ回答を採点するには採点器の拡張（または回答を採点前に ref へ変換する手順）が必要になる。本 PR はドキュメントのみで、コードは変更しない。採点器の対応方法は実験着手前に確定する。

### 判定式

```text
差 = 成功率(簡約方式) − 成功率(生 DOM 方式)    （全体・25 件）
判定: 差 ≥ −5pt なら AISNAP-9 を達成とする
```

- 成功率は `合格数 / 25 × 100`。1 件が 4pt に相当するため、取りうる差は 4pt 刻みである。したがって `≥ −5pt` は実質「簡約方式の合格数が生 DOM 方式より 1 件以上少なくならない」を意味し、1 件差（−4pt）までは達成、2 件差（−8pt）で未達となる。
- 種別別（click・extract・form・nav）とページ別（13 ページ）の差も併記する。これらは判定には使わず、全体判定の内訳として示す。種別別は 6〜7 件、ページ別は 1〜数件しかなく、統計的な有意性は主張しない。

## 限界

レポートには次を必ず明記する（#123 のオーナー判断）。

- **粒度が粗い**: 25 件では 1 件が 4pt に相当し、判定は粗い。−5pt の閾値は 1 件差と 2 件差の間に位置し、回答のばらつき 1 件で判定が反転しうる。
- **簡約方式に甘い**: 合成 fixture は小さく、大規模ページを想定した比較より簡約方式に甘くなる。生 DOM が長大になるほど生 DOM 方式の成功率は下がるはずだが、本実験の fixture ではその差が現れにくい。逆に言えば、本実験で差が −5pt 以内でも大規模ページでの同等性は示さない。PoC-4 が時間制約で見送った Wikipedia 記事（約 31 万トークン）級の条件は本実験の範囲外である。

加えて本書の設計に由来する限界を記す。

- 合成 fixture は実サイトと内容が異なる（`harness/agent_eval/README.md`「PoC との差分」）。PoC の実測値（22/25）との比較は参考扱いである。
- サブエージェントの手動実行は再現性が低く、同じ入力でも回答がぶれうる。1 タスク 1 試行のため、ぶれの大きさは測れない。
- 方式間で回答形式が異なる（ref 対ロケータ）ため、純粋な「表現の良し悪し」だけを比較しているわけではない。
- 簡約表現は現時点で暫定行形式（`AISNAP-6` 確定前。`harness/agent_eval/README.md`）で、確定応答形式が変われば結果は再測定が必要になる。

## API 経由の LLM 自動実行を採らない理由

API 経由で LLM を自動実行すれば再現性と規模を得られるが、費用の負担と秘密情報（API キー）の扱いに関する判断が必要になるため採用しない（#123 のオーナー判断）。
判断が下りた場合は、本書の割付表・指示テンプレートをそのままスクリプトに移せる設計にしてある。
