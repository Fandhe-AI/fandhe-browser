# 同じ role・name の要素の再特定（AISNAP-10）設計

- **対応ビヘイビア**: AISNAP-10（主）、AISNAP-1・AISNAP-4（トークン削減への影響）、AISNAP-6（応答形式への影響）。AISNAP-11・AISNAP-12 は参考
- **対応タスク**: TASK-17 の残課題（差し戻し先候補は TASK-15・TASK-16）
- **マイルストーン**: MS-2
- **関連 Issue**: #926（本 Issue）・#110（判定ヘルパー）・#112（測定レポート）・#113（達成可否の判断。人間担当）・#833・#834（出力 name の補完の前例）

本文書は設計のみで、実装は含まない。実装は文書レビュー後に別 Issue で行う。10% 以下の達成可否の判断は含まない（#113）。

## 目的と非目的

- 目的: 判定ヘルパーの契約（role+name による再特定）を変えずに、参照破損 3 件（[測定レポート](./reference-stability-report.md) の 07・12・18）を解消する方式を決める
- 非目的: 実装、判定ヘルパーの契約変更、10% 以下の達成可否の判断（#113）、トークン削減目標の達成判断（#97・#131）

## 現状

### 判定ヘルパーの契約

`crates/fandhe-browser-ai/src/reference_stability.rs`（#110）は次の手順で判定する。

1. 変化前に、対象の ref と `RefHolder` の `(role, name)` を取る
2. 変化後に、同じ `(role, name)` を持つ ref 保持要素を集める
3. 1 件で ref 同一なら `Stable`、ref が違えば `RefChanged`、0 件なら `SignatureChanged` または `MissingAfter`、複数なら `Ambiguous`

ref 保持要素には、通常ノード、圧縮表のヘッダセル（`HeaderCell`）、行内コントロール（`RowControl`）を含む。name は ref 発行時の出力 name である。

ヘルパーを変えずに `Stable` にする条件は、変化後の出力で対象の `(role, name)` が ref 保持要素の中で一意であること。つまり、出力される name の文字列そのものを区別する必要がある。別フィールドでの区別は、ヘルパーが見る署名に入らないため契約変更になる。

### ref の構成

- ref は `e<8..16 hex>[v<n>][-n]` 形式。ダイジェストの入力は、role・accname（フル name）、`discriminator`（`id`・`href` 等）、親 ref による scope
- #833・#834 の前例では、出力 `Node::name` だけを補い、ref シグネチャ（accname）は変えなかった。このため ref の文字列は不変で、既存の ref 安定性は壊れない
- 本件の区別子も同じ方針にできる。ref の算出後に付ける後段のパスとする

## 3 ケースの重複構造

`build_snapshot` の実出力で確認した（実測）。generic のラッパーは折り畳まれ、出力木は平坦になる。

| ケース | 重複の構造 | 出力木上の区別点 | 変化で区別点が変わるか |
| ------ | ---------- | ---------------- | ---------------------- |
| 07 | 1 件目は 1 つ目の `.quote` 内のタグ（`href=/tag/alpha/page/1/`）。2 件目は右サイドバー `Top Ten tags` 内（`href=/tag/alpha/`） | 1 件目の直前は引用文 generic、2 件目の直前は heading `Top Ten tags`。出現順は 1 番目と 2 番目 | 変化は対象より後ろ。変わらない |
| 12 | `table#table1` と `table#table2` のヘッダ 1 列目。どちらも圧縮表の `HeaderCell` | 直前の `h4` が `Example 1` / `Example 2`。表の `id`。表の出現順 | 変化は対象より前だが、直前の見出しは変わらず、同グループ内の出現順も変わらない |
| 18 | 引用ごとの `(about)` リンク（`href=/author/author-N`） | 直前の引用文 generic が互いに異なる。heading `Quotes to Scrape` は共通で、見出し文脈だけでは区別できない | 変化は banner の追加のみ。同グループ内の出現順は変わらない |

- 共通点: 重複は変化前から存在し、変化はグループ内の出現順を変えない位置関係にある
- 同じページには他にも重複がある（`gamma`・`epsilon` 等のタグが引用間とサイドバーで重複）。区別子は 3 ケース専用でなく一般則として設計する
- 重複する対象には `HeaderCell` と `RowControl` も含める

## 設計制約

- ref 文字列は変えない。区別子は後段のパスで付け、accname は変えない
- 判定ヘルパーの契約は変えない。したがって区別子は出力 `name` に入れる
- 変化前後で同じ文字列になること（バナー追加等で変わらない）
- 決定的な出力であること
- ページ由来の name が区別子の文字列と衝突し得る（例: ページ上に `alpha #2` というリンクがある）
- 区別子にページ由来の長い文字列を入れない（トークン増・プロンプトインジェクション面）

## 契約を変えない限り解消できないケース

3 ケースはすべて、契約を変えずに解消できる見込み（案 A・A2・B）。次の場合は解消できず、3 ケースには含まれない。

- 同じ `(role, name)` の要素が対象より前に挿入される変化（出現番号がずれる）。ref 側も同一ダイジェストの出現番号 `-n` がずれる原理的な限界がある。参照安定性の測定は、同 role・base name の要素数が増えた変化を `Ambiguous` として検出し、`Stable` とは判定しない（誤同定を成功にしない）
- 重複グループの要素数が変わる変化。案 A では 1 件が重複になる、または重複が解消すると name が変わる。案 A2 では先頭が素の name のままなので、後ろに増えても `Stable` のまま
- 同じ文脈で同じ name の要素が並ぶ場合の入れ替え（出現番号が入れ替わる）

これらは案 D・E（契約変更）なしには解消できない。契約変更はオーナー判断（#113）で、判断材料は次のとおり。

- トークン増がゼロ
- ref 同一性の診断値 0/18 と整合する
- 判定基準の変更に当たる

## 推奨案

**案 A2**（出現順。先頭は素の name、2 件目以降に `#n`（直前に半角スペース））を推奨する。

- 3 ケースを契約変更なしで解消する見込み
- 最小コスト。1 件あたり 2〜3 トークンで、17 ページでの増は 0〜12%
- 後ろに同名要素が増えても先頭の要素は `Stable` のまま（リストが伸びる変化への耐性）
- 実装は ref 発行後の木を 1 回走査する後段のパスで済み、ref は変わらない

案 B は第 2 段階の候補にとどめる。見出し依存で安定性が崩れる要因が増え、トークン増も大きい。案 A2 の実測で出現順のずれによる破損が問題になった場合のみ検討する。

実装時の要点:

- 重複判定のキーは `RefHolder` の `(role, name)` と同じ定義にそろえる
- 付与は `build_snapshot_inner` の末尾で行う。対象は ref 保持ノード、`TableSummary.header` の `HeaderCell`、`TableRow.controls` の `RowControl`
- 付与後の name がページ由来の name と衝突する場合は、次の出現番号で解消する。反復回数に上限を設け、超えたら `Ambiguous` として検出できる状態にする（fail-closed）
- `build_snapshot_inner` は木の構築途中で `RefHolder.name` を複製して記録し、`reference_stability` はその記録で判定する。後段パスで `Node`・`HeaderCell`・`RowControl` の name だけを変えると、`RefHolder` は元の重複した name のままになり `Ambiguous` が残る。そのため後段パスは、ref をキーに区別子付与後の name を `RefHolder` へも同期する（ヘルパーの契約・`RefHolder` の型は変えない）。この同期は実装 Issue 1 に含める
- 付与後の name の長さは既存の name 上限の内に収め、超える分は元の name 側を切り詰める
- グループ化は `HashMap` で行い、計算量を要素数に対して線形に保つ
- 副作用として `Node::name` は、重複時のみアクセシブルネームそのものではなくなる。#833・#834 にも出力 name の補完の前例がある

## spec 側の課題

`docs/spec` は本リポから編集しない。次はユーザーへ報告する事項。

- AISNAP-10 は再特定を「role+name シグネチャの一致」と定義している。重複する要素の `name` に区別子が付くこと、先頭の要素は素の name のままであることの追記要否
- AISNAP-1・AISNAP-4 の測定対象（行形式テキスト）に区別子のトークンが含まれること
- 現行の記述（ref の表示長・付与対象の限定は実装裁量）で足りるかの最終判断は spec のオーナー

## セキュリティ考慮

- 区別子は定型の短い文字列（`#n`（直前に半角スペース））のみで、ページ由来の長文を足さない。案 B を採る場合も 20 文字に制限し、空白・制御文字を正規化する
- 衝突解消は反復回数に上限を設ける（DoS 防止）
- 案 C は URL 中の資格情報の露出を理由に退ける
- 区別子は UA・フィンガープリント等の識別面を変えない（SEC 系に抵触しない）
