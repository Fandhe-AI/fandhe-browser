# 動的ダッシュボード類型の MVP スコープ判断（TASK-73）

**判定日**: 2026-10-29  
**判定者**: プロジェクトオーナー  
**対象**: `04-behavior/compat-level.md` COMPAT-2（関連 RENDER-4・RENDER-5・RENDER-7、COMPAT-1、PLUG-7）・TASK-73  
**マイルストーン**: MS-6

## 決定事項

判断材料は Issue #317。動的ダッシュボード類型（PoC-1 類型 (e) のうち Canvas・非 DOM 描画が主体のもの。対象サイト群では e5 Grafana）の扱いを、#57（TASK-40）の判断（RENDER-7・段階導入）に合わせて決めた。

1. **動的ダッシュボード類型は段階導入とする**。#57 の判断（RENDER-4 確定・段階導入 A2・v1 は Servo ホストの描画の範囲でスクリーンショットと境界ボックスを提供・RENDER-5 の v1 基準は境界ボックス・SSIM 0.90 は v2 の目標。`rendering-fallback-plan.md`）と同じ段階に揃える。
2. **v1（MVP）で提供するのは、Servo ホストによるスクリーンショットと境界ボックスまで**とする（RENDER-4・RENDER-5。TASK-36・TASK-38）。
3. **Canvas 等の非 DOM 描画からのデータ抽出は v1 の対象外**とする。DOM 抽出と AI スナップショットでの数値取得を含む。
4. COMPAT-2 の判定（spec の更新）は spec リポの PR で別途行う（本書では扱わない）。

## v1 で提供するもの・約束しないもの

### 提供するもの

- ダッシュボードページのスクリーンショット（PNG）の取得（RENDER-4・TASK-36）
- 主要レイアウト要素の境界ボックスの取得（RENDER-5・TASK-38）
- いずれも Servo ホストの描画の範囲に限る。Servo のソースは改変しない（`OSS-2`・`OSS-3`）

### 約束しないもの

- Canvas・非 DOM 描画（`<canvas>` や、`<table>` を持たない `<div>` ベースのグラフ）からのデータ抽出
- DOM 抽出・AI スナップショット（`AISNAP` 系）での、グラフ・パネルの数値の取得
- ダッシュボードの描画が Chromium と同じに見えること（SSIM 0.90 以上は v2 の目標。`rendering-fallback-plan.md`）

## 採らなかった案

COMPAT-2 の期待は「レンダリング層が成立すれば MVP に含めるかを判断でき、成立しなければ除外またはスクショのみの段階導入」としている。#57 で RENDER-4 は達成として確定したため、「含める」「完全に除外」「段階導入」の 3 案から選んだ。

| 案 | 内容 | 採否・理由 |
| -- | ---- | ---------- |
| 含める | v1 で Canvas 等からのデータ抽出まで約束する | 不採用。Canvas の描画結果から数値を取り出すには、画素解析や描画 API の呼び出しの捕捉といった DOM 抽出と別の手段が要り、v1 の範囲に含まれない。約束しても満たせない |
| 完全に除外 | 動的ダッシュボード類型を v1 の対象から外す | 不採用。スクリーンショットと境界ボックスは #57 で v1 に確定済みで、ダッシュボードにも使える。外すと提供済みの能力まで約束から消える |
| 段階導入（採用） | v1 はスクリーンショットと境界ボックス。データ抽出は対象外 | 採用。#57 の段階と揃い、v1 で約束できる範囲を明確にできる |

## 根拠

### 実測

`harness/compat-practical/results/matrix.json`（28 サイト化後。測定条件は `type-report.md`）の類型 (e)（`cat=table`）は次のとおり。

| id | サイト | fandhe-browser-core | Chromium |
| -- | ------ | ------------------- | -------- |
| e1 | GitHub の Issue 一覧テーブル | 失敗 | 失敗 |
| e2 | DataTables のデモ | 成功 | 成功 |
| e3 | Google スプレッドシートの公開ビュー | 成功 | 成功 |
| e5 | Grafana Play | 失敗 | 失敗 |
| e6 | Kaggle のデータセット一覧 | 失敗 | 成功 |
| 計 | - | 2/5（40.0%） | 3/5（60.0%） |

- ダッシュボード類型は e5 の 1 サイトだけで、Chromium も失敗している。core の失敗を core 固有の弱さとは判断できない
- 類型 (e) 全体の core の動作率は 40.0%（2/5）で、`COMPAT-1` の対象 3 類型（static・spa・form）がいずれも 80% 台なのとは別の状態にある（`type-report.md`）
- e5 の core の失敗は `type-report.md` で「未特定（非 DOM 構造の可能性）」と分類している。確定原因ではない（`REPAIR-3`）

### PoC-9 の整理

PoC-9（`03-poc/practical-compat-level/README.md`）は e5 を「非 DOM 構造（レンダリング要）」と整理している。ダッシュボードは Canvas や `<div>` ベースのグラフ描画で、`<table>` 要素自体が無く、JS を実行しても DOM 抽出という手法が原理的に成立しない類型とする。Chromium も同じセレクタで失敗しており、JS 実行の有無ではなく、タスク設計とサイトの描画方式のミスマッチによるとする。この類型を MVP に含めるなら、レンダリング層でのスクリーンショット・座標抽出への切り替えが必須とも述べている。

JS エンジン統合（V8）が済んでも、この類型は DOM 抽出では埋まらない。v1 でデータ抽出を約束できない理由の中心はここにある。

### レンダリング層の判断

- #57（TASK-40）で RENDER-4 を達成として確定し、v1 のレンダリング層はスクリーンショットと境界ボックスを Servo ホストの描画の範囲で提供する段階導入とした（`rendering-fallback-plan.md`、#1305）
- RENDER-5 の v1 基準の測定（#55・TASK-37）は、境界ボックスが 6 サイト中 5 サイトで合格、SSIM 0.90 以上は 1 サイトだった
- PLUG-7 の互換段階では、描画の忠実度は段階 3（レイアウト・描画の忠実度）に当たる。ダッシュボードの見た目の再現はそこで扱い、v1 の約束には含めない

## 既知の限界・後続

- **ダッシュボードの描画を直接確かめた測定はない**: #55 の測定 6 サイト（a1-wikipedia・a2-mdn・a3-rust-book・a4-python-docs・b1-react-dev・c6-hacker-news）に、ダッシュボードや Canvas 系のサイトは含まれない。Servo ホストが Grafana のような Canvas 描画を正しく描けるか、スクリーンショットと境界ボックスが実用になるかは、測っていない。本書の判断は「v1 で約束する範囲」を決めたもので、描画できることを確かめたものではない
- **サンプルが 1 サイト**: 類型 (e) のうちダッシュボードに当たるのは e5 だけ（e4 は公開ビューを確保できず採用保留。`site-catalog-task70.md`）。類型としての一般化はできない
- **全体動作率での e5 の扱い**: COMPAT-4 の全体動作率（TASK-74・人間担当）で e5 を分母に含めるかは、本書では決めない
- **v2 で再評価する**: v2 の目標水準を決めるとき、SSIM の目標（`rendering-fallback-plan.md`「残る課題・追跡」）と合わせて、Canvas 等の非 DOM 描画からのデータ抽出を扱うか、扱うならどの手段（画素解析・描画 API の捕捉・サイト固有のデータ取得経路）かを検討する
- **spec への反映**: spec リポの PR（番号は後で追記）
